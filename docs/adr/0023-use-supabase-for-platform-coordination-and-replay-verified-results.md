# Use Supabase for platform coordination and Replay-verified results

The current-view/Replay hash correspondence in this decision is corrected by
[ADR 0025](0025-verify-current-and-replay-public-view-correspondence.md), approved
on 2026-09-07. Each original wrapper is hashed independently; the exact
same-Head public content must agree, with only `viewer_class` differing.

## Context

[ADR 0019](0019-separate-hosted-activity-platform-from-worldstream.md)
separates the Hosted Activity Platform from WorldStream,
[ADR 0020](0020-use-vercel-for-control-and-fly-for-direct-browser-streams.md)
places HTTPS product control on Vercel and realtime Room authority on Fly, and
[ADR 0021](0021-use-reviewed-pre-genesis-formation-for-hosted-activity-runs.md)
defines pre-Genesis formation. Those decisions did not identify the durable
owner of mutable platform formation or define how a terminal Room becomes a
safe, idempotent public result.

Vercel Functions are stateless. Atomic invitation claims, launch idempotency,
quota reservation, and recovery after an ambiguous Fly reply therefore need a
durable platform store. Treating that store as only a read model would require
a second platform database on Fly and would leave two recovery paths for a
hobby MVP.

Result publication also cannot assume that every Activity Pack uses fields
named `phase`, `outcome`, `winner`, or `score`. Agent Heist and Negotiate have
different terminal and Outcome shapes. A client-submitted result or a generic
JSON-path convention would duplicate Pack authority and fail across Packs.

This decision freezes the MVP Supabase schema boundary, authentication and
grant model, result-projector contract, and cross-system reconciliation rules.

## Decision

Use Supabase Auth and Postgres as the authority for **platform-only** identity
and coordination. Keep WorldStream on Fly authoritative for every Room fact.

```text
GitHub OAuth
    |
    v
Vercel BFF ----------------------> Supabase platform_store
    |                              accounts, formation, Run correspondence,
    |                              immutable result evidence, public index
    |
    +---- authenticated pull ----> Fly / WorldStream
                                   Genesis, Membership, Projection, Outcome,
                                   Complete Head, integrity, Replay
```

The boundary is strict:

- Supabase owns Platform Accounts, Launch Requests, Seat Claims, Seat
  Invitations, platform quota reservations, immutable House Agent
  Assignments, and their Host-operation correspondence.
- Supabase records an Activity Run only after Fly proves Room Genesis.
- Supabase holds a non-authoritative Indexed Activity Result only after Vercel
  projects authorized Fly evidence into a publishable summary and healthy
  integrity and verified Replay agree through the exact source Head.
- Fly and WorldStream own Core Room State, Membership, Activity Phase, Actions,
  legality, Outcome, Complete Heads, integrity, Canonical History, and Replay.
- Checked-in canonical Activity Listing Revision documents remain catalog
  authority. Their Supabase rows are immutable deployed copies.
- Supabase stores no Room materialization, Membership credential, private
  Projection, Replay bytes, model credential, prompt, reasoning trace, or
  provider response.
- Browser code, Activity Packs, Activity Clients, House Runners, and Fly hold
  no Supabase database key and have no database write path.

### Database schemas

Create two application schemas:

| Schema | Exposure | Contents |
| --- | --- | --- |
| `platform_store` | Never exposed through the Supabase Data API | All base tables |
| `platform_api` | The only application schema exposed through the Data API | Enumerated server-only RPC functions; no tables or views |

The Supabase `public` schema contains no application objects and is removed
from the exposed application schemas or left empty with all default grants
revoked. Application objects are never created in the managed `auth`,
`storage`, or `realtime` schemas.

Every identifier, string, JSON value, and byte sequence has an explicit bound.
Times are UTC `timestamptz` values supplied by the database. Content IDs use a
lowercase `algorithm:hex` representation; Listing Revision identities use
`blake3:` followed by 64 lowercase hexadecimal characters.

### Platform identity tables

`platform_store.platform_accounts` is a stable pseudonymous platform identity:

- `account_id uuid` primary key, generated by Postgres;
- `created_at`; and
- nullable `erased_at`, which never precedes `created_at`.

Successful Runs reference the Platform Account with `ON DELETE RESTRICT`.
Deleting an account therefore removes login and display information while
retaining a random tombstone needed by shared history. That tombstone has no
provider or profile fields, but it remains linkable across retained Runs and
must not be described as anonymous or fully deidentified.

`platform_store.github_identities` is the mutable and deletable login edge:

- `auth_user_id uuid` primary key referencing `auth.users(id)` with
  `ON DELETE CASCADE`;
- unique `account_id` referencing `platform_accounts`;
- provider fixed to `github`;
- unique `(provider, provider_subject)`, where the subject is copied only from
  a server-verified Supabase User Identity;
- optional current GitHub login and avatar URL used only for presentation;
- `public_profile_enabled`, default `false`;
- nullable `erasure_requested_at`; and
- `linked_at` and `refreshed_at`.

GitHub login, email, avatar, and Supabase user metadata never authorize an
operation. The Vercel OAuth callback creates the Platform Account lazily and
refreshes presentation data. The MVP enables GitHub OAuth only; anonymous Auth
and manual identity linking are disabled. Once `erasure_requested_at` is set,
normal identity sync cannot clear or reactivate that edge.

`platform_store.oauth_login_attempts` is the bounded one-use PKCE correlation
store. It contains a random attempt identity, SHA-256 state digest, encrypted
PKCE verifier, browser-nonce digest, allowlisted return target, creation and
ten-minute expiry times, and nullable consumption time. The OAuth state and
browser nonce are stored only by digest, and the verifier is never stored in
plaintext; it uses authenticated encryption under a separately rotatable
Vercel-only key. The callback atomically consumes an unexpired matching state
before decrypting the verifier and exchanging the one-use provider code.
Expired rows may be deleted by the bounded daily maintenance path because they
are neither Platform Accounts nor shared activity history.

### Catalog and formation tables

`platform_store.activity_listing_revisions` is an insert-only deployed copy of
one checked-in Listing Revision. It records:

- `listing_revision_digest` as the primary key and stable `listing_key`;
- bounded canonical document bytes;
- exact Pack Revision and Activity Client Release digests;
- exact Client Surface identity;
- immutable catalog visibility `public`, `unlisted`, or `private`;
- creator access policy `must_claim_seat` or `may_spectate`;
- `public_viewing_policy` as `disabled` or `anonymous_by_link`;
- `result_publication_policy` as `disabled` or
  `public_recent_results`;
- exact Result Projector Revision digest, accepted Public Projection
  schema, output schema, canonicalizer version, and output-byte bound; and
- `deployed_at`.

Every launchable hosted Listing pins the projector because its terminal or
nonterminal disposition releases platform capacity without teaching shared
code Pack-specific phases. When publication is disabled, the platform discards
any projected summary and creates no Indexed or Published Activity Result.
There is no mutable catalog-head table in the MVP. Vercel's checked-in catalog
selects discovery, while old database rows remain for accepted Launch Requests
and Runs.

Every result output field is privacy-reviewed with the Listing Revision. The
MVP schemas admit only fixed enums, numbers, booleans, timestamps, and reviewed
bounded labels. They do not admit arbitrary Pack, Projection, participant, or
user-authored free text. A later Listing that needs such text requires a new
privacy review, projector revision, output schema, and purge policy.

`platform_store.launch_requests` is the mutable pre-Genesis coordination row:

- `launch_request_id uuid` primary key;
- creator Platform Account and exact Listing Revision;
- idempotency namespace and hashed idempotency key;
- canonical launch-input bytes, digest, and canonicalizer version;
- the exact House-fill choice;
- the creator's frozen seat-or-spectator choice;
- state limited to `collecting_roster`, `provisioning`, `reconciling`,
  `run_created`, `cancelled`, `expired`, or `failed_pre_genesis`;
- expiry, creation, and last-transition times;
- nullable roster-freeze time and canonical frozen Room Setup Specification
  bytes and digest;
- nullable Host installation and Room Setup Operation identities; and
- nullable `host_mutation_started_at`, set in the same transaction that
  authorizes the first Fly mutation and never cleared.

The table has unique constraints on
`(creator_account_id, idempotency_namespace, idempotency_key_digest)` and on a
non-null `(host_installation_id, room_setup_operation_id)`. The stable Room
Setup Operation identity is stored before Vercel makes the first Fly setup
call. State transitions, quota reservation, and roster freezing occur only in
transactional RPCs. No launch mutation is allowed after `run_created` except
retained reconciliation bookkeeping outside this row.

`platform_store.capacity_reservations` has a generated reservation identity,
Launch Request, kind `pre_genesis` or `active_run`, class `authorized` or
`quarantined_recovery`, controlling account, nullable Run, reservation and
release times, and a typed release reason. A partial unique index permits only
one unreleased row per `(launch_request_id, kind)`, while released history is
never reopened. Other partial unique indexes permit at most one unreleased
`pre_genesis` reservation and one unreleased authorized `active_run`
reservation per creator account. A quarantined-recovery `active_run` row is
allowed only while recording Fly-proven Genesis that lacked a valid current
authorized reservation; it is unique per Run and does not make the launch
valid retroactively.
`platform_store.capacity_gates` contains exactly one migration-owned
`active_run` row with the MVP hard limit of ten; it stores no mutable counter.
Launch creation acquires `pre_genesis`. Before the first Fly mutation, another
transaction locks the Launch Request, every controlling account, the gate row,
and then the account's reservations in that fixed order. It proves that the
request is still eligible and no controlling account is erased, counts
unreleased `active_run` rows, acquires `active_run`, and sets
`host_mutation_started_at`. Only that committed transaction authorizes Vercel
to perform the first retained Fly operation. Every acquisition and release
uses the same applicable lock order. Genesis releases only `pre_genesis` and
attaches the Run to the already-held `active_run` reservation. A reconciled
pre-Genesis failure or pre-start abandonment releases both. The pinned
projector's terminal disposition releases `active_run`. An ambiguous Fly state
retains every applicable reservation, and an ordinarily authorized Genesis
never needs to win capacity after the Room exists.

`platform_store.seat_invitations` contains a generated invitation identity,
Launch Request, fixed seat ID, generation, token digest, expiry, consumption,
revocation, and creation data. It never stores the raw token. Rotation locks
the Launch Request, revokes the prior generation, and creates the next one in
one transaction. Token digests are globally unique, and
`(launch_request_id, seat_id, generation)` is unique.

`platform_store.seat_claims` contains a generated claim identity, Launch
Request, fixed seat and Role, controlling Platform Account, participation kind
(`account_human` or `account_external_agent`), a planned setup-local Principal
reference, and claim/release times. Vercel derives references from reserved
namespaces such as `seat:{seat_id}`; browser input cannot supply one.
Provisioning allocates a new run-scoped Principal from that reference; a
Platform Account does not reuse one stable WorldStream Principal across Rooms.
A partial unique constraint permits only one unreleased claim per Launch
Request seat. The claim RPC locks the Launch Request and seat so concurrent
claimants have exactly one winner. The
one-seat-per-account rule and its reviewed solo-test exception are checked
from the pinned Listing Revision inside the same transaction.

`platform_store.house_agent_assignments` holds the immutable pre-Genesis
assignment required by ADR 0022. Its unique `(launch_request_id, seat_id)`
identity references one House Fill Operation and pins the exact House Agent
Revision, server-derived setup-local Agent Principal reference, provider and
model route, Runner identity and reservation receipt, policy and template
revisions, accounting tokenizer, and hard execution allowance. It contains no
provider secret, prompt, response, or detailed model-call log.

`platform_store.house_fill_operations` contains one durable operation per
eligible Launch Request. It records its stable operation identity, final
claim-window close time, state (`waiting`, `reserving_runners`, `assigned`, or
`failed_pre_genesis`), and, after the window closes, bounded canonical
candidate and exclusion sets, their digests, the retained cryptographic draw,
selected revision identities, exact Runner-capacity reservation identities,
and a typed failure reason. The candidate set, exclusions, draw, selections,
and reservation identities become immutable together when the draw transaction
locks the Launch Request and claims and moves the operation to
`reserving_runners`. It creates no House Agent Assignment yet.

`platform_store.house_runner_reservation_receipts` is append-only and records
one authenticated terminal Fly receipt for each retained Runner reservation
operation. An exact retry is idempotent; a contradictory receipt quarantines
the fill. Vercel idempotently reconciles only the retained operations with Fly.
After every selected reservation succeeds, `complete_house_fill_v1` locks the
operation and receipts and atomically creates the immutable House Agent
Assignments, freezes their successful receipt digests, and moves the operation
to `assigned`. A terminal failure moves it to `failed_pre_genesis` without
creating any Assignment. A retry reads or resumes this same operation and
cannot open another window, draw again, partially create an assignment set, or
select a replacement.

Invitation, claim, and House Assignment rows cannot change after the Launch
Request roster freezes. Genesis promotes every provisioned Room Membership
into an immutable Run Membership Correspondence; post-Genesis entry never
relies on a mutable Seat Claim.

Every hosted launch adds the platform-controlled Result Indexer Principal's
Spectator Membership to the frozen Room setup. It supplies the authorized
Public Projection used for terminal-capacity reconciliation and, when enabled,
result publication. Its server credential has exactly `room:attach`,
`room:observe_public`, and `room:replay`; Spectator Access Mode alone does not
imply Replay authority. Replay requests are fixed to the public projection kind
and cannot request a participant view or Final Reveal. It is not a Pack seat,
does not receive a Pack Role, and does not affect
participant cardinality. A hosted Listing cannot reach Genesis if this
Membership and its scoped server credential cannot be provisioned. Anonymous
live viewing independently adds the Public Projection Relay's different
Spectator Membership with exactly `room:attach` and `room:observe_public`, but
no Replay scope, when that policy is enabled.

When the creator elects to spectate under a `may_spectate` Listing, the frozen
setup also provisions one run-scoped Human Principal and Spectator Membership
for that account. Its browser admission receives `room:attach` and
`room:observe_public` only; Replay is excluded from the MVP. It receives no
seat or Pack Role. A creator who neither claims a seat nor has this reviewed
option receives no Room Membership.
`creator-spectator`, `result-indexer`, and `public-relay` are also
server-derived reserved Principal references.

The current Room Setup Specification v1 can allocate only participant seats
and an Operator view; it cannot express these Spectator Memberships. Hosted
implementation therefore requires a versioned, bounded non-seat-spectator
field or an equivalently frozen narrow Host launcher contract. It may not map
platform spectators to Operator Memberships or reuse participant credentials.

### Activity Run and Membership correspondence tables

`platform_store.activity_runs` is insert-only and contains:

- `run_id uuid` primary key and unique `launch_request_id`;
- exact Listing Revision and creator Platform Account;
- private Host installation, Room Setup Operation, and Room identities;
- Genesis sequence, `genesis_or_transition_hash`, and canonical Genesis
  evidence digest;
- nullable 32-hex-character `public_id`, generated from 16 random bytes only
  after Genesis when live viewing or result publication requires a public URL;
- evidence class `unranked` or
  `exhibition_platform_house_agents`; and
- Genesis observation and insertion times.

Unique constraints cover `(host_installation_id, room_id)`,
`(host_installation_id, room_setup_operation_id)`, and non-null `public_id`.
The table contains no Activity Phase, live status, turn, winner, score,
Outcome, Membership Standing, Projection, or Cursor.

Only a Run whose Listing enables `anonymous_by_link` binds its `public_id` to
the exact Room through a separate idempotent Fly operation after the database
transaction. A result-only Run uses the ID solely in Vercel and Supabase; it is
never resolvable by Fly's live-view endpoint. A live URL is not advertised
until its binding succeeds. A repeated identical binding succeeds; a different
Room or identifier conflicts.

`platform_store.activity_run_memberships` is an immutable private admission
snapshot with primary key `(run_id, membership_id)`. Each row records:

- Access Mode and purpose: `participant`, `creator_spectator`,
  `result_indexer`, or `public_projection_relay`;
- nullable exact seat and Role plus one reviewed, non-user-authored public seat
  label;
- WorldStream Principal kind;
- nullable participation source `account_human`, `account_external_agent`, or
  `platform_house_agent`;
- nullable controlling Platform Account;
- private Principal and Membership correspondence;
- a selector encoded from 16 random bytes for each account-controlled
  Membership, non-secret and unique within the Run;
- nullable exact capability-scope-set digest for a platform-service
  credential;
- nullable exact House Agent Assignment; and
- Genesis promotion time.

Participant rows require Participant Access Mode, seat, Role, and participation
source. Human rows require a run-scoped Human Principal and account;
external-agent rows require a run-scoped Agent Principal and account; House
rows require an Agent Principal and House Assignment with no controlling
account. Every other purpose requires Spectator Access Mode and no seat or
Role. Creator spectators require an account and Human Principal; the two
platform-service purposes require Agent Principals, no account, and their exact
reviewed scope set. Unique constraints cover each non-null
`(run_id, seat_id)`, each non-null `(run_id, entry_selector)`, each Principal
and Membership identity in the one operated Host, and `(run_id, purpose)` for
every non-participant purpose. The frozen Listing determines which purposes
are required, and
`record_genesis_v1` rejects an incomplete or extra set. No display name or
client-claimed agent metadata is copied into this immutable table.

`read_owned_run_v1` returns each account-controlled Membership's reviewed seat
label, purpose, and opaque entry selector but never its Principal or Membership
identity. `resolve_owned_run_membership_v1` accepts the server-resolved Platform
Account, Run, and selector, verifies the exact correspondence, and returns its
private identities only to the BFF. The BFF then asks Fly for a fresh one-use
Activity Client handoff. The selector grants nothing without the authenticated
account, is not a Membership credential, and remains unambiguous when a
reviewed solo-test Listing lets one account control more than one participant
row. Browser input never supplies a Principal or Membership ID.

### Result Projector Revision

Every launchable Activity Listing Revision pins one exact, content-identified
**Result Projector Revision**. It is reviewed platform code deployed with the
Vercel application, not a sixth Activity Pack operation and not Activity
Client code.

The projector is deterministic, networkless, environmentless, time- and
memory-bounded, and loaded only when its built artifact matches the pinned
digest. It accepts only:

- the exact compatible Pack Revision and Listing Revision identities;
- canonical bytes for the dedicated result-indexer Membership's authorized
  Public Projection;
- the accepted Public Projection schema identity; and
- the exact source Head.

It returns exactly one of `not_terminal`, `terminal_without_outcome`, or a
bounded public summary that validates against the pinned output schema. Only
the final case is publishable. Pack-specific terminal and Outcome
interpretation remains inside the reviewed projector; shared reconciliation
code contains no Heist, Negotiate, `phase == complete`, `winner`, or `score`
branch.

Changing projector code, input interpretation, output schema, or
canonicalization creates a new Listing Revision for future Runs. An earlier
Run never rebinds to the new code.

The Platform Operator retains every content-addressed projector artifact,
canonicalizer, runtime revision, and verification fixture referenced by an
existing Run. Delisting or deploying newer code does not remove them. A release
cannot claim rebuildability unless CI can resolve and execute every retained
projector identity; garbage collection requires a later retention decision
that also ends the rebuild promise for affected Runs.

### Terminal-capacity evidence

`platform_store.activity_run_terminal_evidence` is insert-only with one row per
Run. It stores the exact Listing and Result Projector Revision, source Complete
Head, Public Projection schema and hash, projector disposition
`terminal_without_outcome` or `terminal_with_summary`, authenticated Host
evidence-envelope digest, and insertion time. It stores no Activity Phase,
Outcome, Projection bytes, or result summary.

`record_run_terminal_v1` inserts that first evidence and releases the Run's
`active_run` capacity reservation atomically. An exact retry is idempotent. A
valid later Head with the same terminal disposition adds a `terminal`
reconciliation receipt without replacing the first evidence; an older Head is
stale. The same source or a valid later Head producing any different terminal
disposition is a terminal contradiction; the locked terminal transaction routes
to the exact conflict transition exposed as `record_terminal_conflict_v1`.
That operation also handles the same source or a valid later Head that projects
as `not_terminal`. It atomically appends a
`result_conflict_quarantined` event and conflict receipt, suppresses any public
result, and permanently blocks first publication for that Run. It never
reacquires or transfers released capacity.

### Indexed result tables

`platform_store.indexed_activity_results` is immutable internal evidence with
one row per `run_id`. It records:

- exact Listing, Pack, result-policy, Result Projector, and result-schema
  identities;
- the dedicated result-indexer Membership identity;
- the Run's Room identity plus every remaining field of the Complete Head for
  which the projector yielded its final summary: Room sequence,
  Genesis-or-Transition hash, Core schema version, Pack digest, Core state
  hash, Activity state hash, and authoritative state hash;
- healthy Room-integrity generation;
- authorized Public Projection schema, payload digest, and `projection_hash`;
- Replay verifier revision, verified-through Head, Replay `projection_hash`,
  and verification receipt digest;
- authenticated Host evidence-envelope digest;
- canonical public-summary digest; and
- indexing time.

The Run's unique Listing Revision already pins one policy, so `run_id` is the
one-result uniqueness key. No universal winner, score, or cross-Pack ranking
column exists.

`platform_store.indexed_activity_result_payloads` stores the corresponding
output schema, exact bounded canonical JSON bytes, digest, and insertion time.
It is insert-once and normally immutable. Keeping payload bytes separate allows
an exceptional offline privacy purge while preserving a result digest and
reconciliation tombstone. The digest can remain linkable and is never exposed
or described as non-personal merely because the payload bytes are gone.

`platform_store.activity_run_index_events` is append-only and contains bounded
typed exceptions:

- `abandoned_prestart`;
- `result_suppressed_integrity`;
- `result_reverified`;
- `result_conflict_quarantined`;
- `result_suppressed_privacy`; and
- `result_payload_purged`.

Each event records Run, optional result, a safe reason code, optional source
evidence digest, optional integrity generation and observed Head, observation
time, and insertion time. Integrity suppression and re-verification require
the generation and Head, and re-verification also requires the Replay receipt
digest. A partial unique constraint permits one accepted suppression or
re-verification per `(run_id, integrity_generation)`.
`record_integrity_observation_v1` locks the Run and result and compares the
latest accepted generation: a lower generation is stale and writes a receipt
only. At the same generation, the same integrity status is idempotent even when
a valid descendant Head or freshly authenticated envelope differs; Head and
summary agreement remain terminal/result reconciliation concerns. A
contradictory integrity status at the same generation appends
`result_conflict_quarantined`. A healthy observation may re-verify only at a
strictly later generation, only after Replay verifies through its exact Head,
and only when the pinned projector yields the existing summary digest. A
divergent valid summary appends conflict quarantine instead. Invalid,
unauthenticated, wrong-Run, wrong-schema, or non-descendant-Head evidence writes
a blocked receipt and cannot suppress a result.

Public reads do not use observation timestamps or insertion order. Conflict
quarantine, privacy suppression, or payload purge always means unavailable.
Otherwise reads start from the Indexed Activity Result's capture generation
and fold only the greatest accepted integrity generation: suppression hides
the summary and attribution, while valid re-verification restores visibility.
These are platform publication or capacity facts, not Pack Activity Phases.

`platform_store.reconciliation_receipts` is append-only operational evidence.
It records subject kind (`genesis`, `terminal`, `result`, or `integrity`),
bounded source key, evidence-envelope digest, disposition (`applied`,
`duplicate`, `conflict`, `blocked`, or `retryable`), optional Run/result
reference, safe error code, and observation time. It stores hashes and typed
codes, never Projection, result, or Replay payloads. No automated
receipt-retention period is added in the MVP.

The required lookup indexes are limited to the supported operations:

- OAuth attempt state digest and expiry;
- Launch Request state/expiry and creator ownership;
- active capacity reservation by class, state, creator, Launch Request, and
  Run;
- invitation token digest and unreleased claim by Launch Request seat;
- House Fill Operation by Launch Request and state;
- House Runner reservation receipt by fill operation and retained reservation
  operation identity;
- Run public ID, Launch Request, Host operation, and Host Room correspondence;
- Run Membership controlling account, purpose, and opaque entry selector;
- result by Run and chronological recent results by Listing identity; and
- reconciliation subject/kind and observation time.

There is no generic JSON index, full-text index, public participant directory,
or leaderboard index in the MVP.

### Authentication and browser boundary

The browser begins GitHub OAuth through a fixed Vercel route. Vercel generates
256 bits of OAuth state, a PKCE verifier, and an independent browser nonce. It
stores only their protected forms in the one-use OAuth attempt and sets the
nonce in `__Host-worldstream-oauth`: `Secure`, `HttpOnly`, `SameSite=Lax`,
`Path=/`, no `Domain`, and `Max-Age=600`. The exact production callback
requires the returned state, that browser nonce, the unconsumed database row,
and the PKCE exchange to agree. It clears the OAuth cookie with the same
attributes on every terminal callback outcome.

Successful sign-in returns only an encrypted, authenticated
`__Host-worldstream-session` cookie with `Secure`, `HttpOnly`, `SameSite=Lax`,
`Path=/`, no `Domain`, and a seven-day maximum age. Vercel rotates its value
after sign-in and every token refresh and clears it with the same attributes on
sign-out or erasure. Authenticated and cookie-refreshing responses use
`Cache-Control: private, no-store`.

Vercel creates two separate Supabase clients per request path:

1. a request-scoped Auth client that verifies ordinary protected reads with
   `getClaims()` and every low-volume state-changing operation with
   `getUser()`, using the publishable key plus the request's Auth cookies; and
2. a standalone secret-key database client that never receives a user access
   token.

The account-erasure worker uses a separately constructed Auth Admin client and
an independently rotatable server-only secret key. Both secret-key clients
still carry the Supabase project's elevated `service_role` authority; their
separation prevents session-token override and improves isolation and rotation,
but is not a database privilege boundary. Neither client establishes the
calling user's identity.

`getSession()` data, a browser-supplied account ID, GitHub profile data, or
user metadata never authorizes an application operation. Vercel resolves the
verified Auth user to a Platform Account and ignores any account or creator ID
in a request body. Every protected route also rejects an erased account or a
GitHub identity with `erasure_requested_at`. Every mutation applies the exact
Origin, Fetch Metadata, CSRF, method, media-type, rate, and size checks from
ADR 0020.

### Grants, RLS, and functions

Supabase secret keys execute as `service_role`, bypass RLS, and are master keys
for the project data and administrative APIs that accept them. RLS is therefore
defense in depth against accidental future exposure, not the authorization
mechanism for Vercel's secret-key calls. The Vercel BFF checks the verified
session; narrow RPCs, object grants, and database constraints enforce the
application operation. This design does not claim that the secret key itself
is globally least-privileged.

The exact grant model is:

| Role or caller | `platform_store` | `platform_api` |
| --- | --- | --- |
| `PUBLIC`, `anon`, `authenticated` | No schema, table, sequence, or function privileges; RLS has no allow policy | No usage or execute privilege |
| Vercel secret-key data client | Schema usage and only the aggregate table operations required by the enumerated RPCs | Schema usage and execute on the enumerated RPC signatures only |
| No-login migration owner | Owns objects; unavailable to applications | Owns objects; unavailable to applications |
| Offline maintenance role | Exceptional privacy suppression/payload purge only | Not deployed to Vercel or Fly |
| Fly, Pack, Activity Client, House Runner | No role and no key | No role and no key |

RLS is explicitly enabled on every base table. Default privileges for tables,
sequences, and functions are revoked from `PUBLIC`, `anon`, `authenticated`,
and `service_role`; required `service_role` privileges are then granted
explicitly in the same migration. These object grants narrow access inside the
application schemas, but do not remove the secret key's elevated authority in
other Supabase services or managed schemas.

Every exposed `platform_api` routine is `SECURITY INVOKER`, uses an empty
`search_path`, fully qualifies every object, has bounded typed arguments and a
bounded DTO result, and is executable only by `service_role`. Postgres grants
function execution to `PUBLIC` by default, so each exact signature is revoked
before its explicit grant. No exposed security-definer function, table, view,
generic SQL, generic operation, caller-selected role, URL, or upstream exists.

The deployed Vercel role receives:

- `SELECT`, `INSERT`, and only required transition-column `UPDATE` privileges
  on mutable account, identity, capacity, and formation tables;
- exact `DELETE` only on consumed or expired OAuth attempts through its
  maintenance RPC;
- `SELECT` and `INSERT`, but no `UPDATE` or `DELETE`, on Listing Revisions,
  House Runner reservation receipts, Runs, Run Memberships, terminal evidence,
  Indexed Activity Results, result payloads, index events, and reconciliation
  receipts; and
- no result-payload purge privilege.

Immutability triggers additionally reject application `UPDATE` or `DELETE` on
Listing Revisions, House Runner reservation receipts, Runs, Run Memberships,
terminal evidence, result evidence, index events, and reconciliation receipts.
They are a backstop, not a replacement for grants.

### Server RPC surface

The normal deployed function allowlist is:

- `begin_github_oauth_v1`, `consume_github_oauth_v1`,
  `purge_expired_oauth_attempts_v1`, `sync_github_identity_v1`,
  `set_public_profile_v1`, and `begin_account_erasure_v1`;
- `create_launch_request_v1`, `read_launch_request_v1`,
  `cancel_launch_request_v1`, `expire_launch_request_v1`, and
  `record_pre_genesis_failure_v1`;
- `claim_invited_seat_v1`, `release_seat_claim_v1`,
  `rotate_seat_invitation_v1`, and `reset_seat_claim_v1`;
- `start_house_fill_v1`, `complete_house_fill_v1`, and
  `record_house_runner_reservation_v1`;
- `freeze_launch_request_v1` and `authorize_host_mutation_v1`;
- `read_genesis_reconciliation_v1`, `read_terminal_reconciliation_v1`,
  `read_result_reconciliation_v1`, and
  `read_integrity_reconciliation_v1`;
- `record_genesis_v1`, `record_prestart_abandonment_v1`, and
  `record_run_terminal_v1`;
- `record_terminal_conflict_v1`, `record_result_v1`, and
  `record_integrity_observation_v1`;
- `resolve_owned_run_membership_v1`;
- `read_owned_run_v1`, `read_public_run_v1`, and
  `list_recent_results_v1`; and
- bounded `list_reconciliation_candidates_v1` and
  `list_pending_account_erasures_v1`.

No function accepts a generic table, query, Host operation, Pack Action, URL,
or caller-selected account identity. `list_recent_results_v1` is chronological,
limited to at most 20 results, and scoped to one Listing identity. It is not a
leaderboard. The MVP implements Agent Heist Recent Results only.

Cancel and expiry require `host_mutation_started_at` to be null. Before that
boundary, every transition that ends a request without a Run is proved by the
exact locked platform state in the same transaction: user cancellation,
database-time expiry, account erasure, or a terminal formation failure such as
an insufficient frozen House pool. After that boundary, a pre-Genesis failure
or pre-start abandonment operates only on the retained exact Host operation
and requires an authenticated matching Fly evidence envelope. Each transition
releases only its applicable reservations.
House-fill RPCs can create or reconcile one retained draw but cannot accept
candidate, selection, Principal, Runner, provider, or model identities from a
browser. Profile toggle and user cancel resolve the verified Platform Account
in the BFF and ignore any body-supplied account identity. There is no generic
capacity-release RPC; only these exact lifecycle transitions release their
corresponding reservations.

### Genesis reconciliation

Vercel generates and stores the Launch Request's stable Room Setup Operation
identity before calling Fly. A lost or ambiguous reply always queries or
resumes that exact operation.

`record_genesis_v1` locks the Launch Request and performs one transaction:

1. Verify the frozen Listing, Pack, roster, Room Setup Specification, House
   Agent Assignments, `host_mutation_started_at`, controlling-account erasure
ordering, and both required capacity reservations. A normal operation must
   have passed the atomic Host-mutation authorization check before Fly.
2. Compare both identities: Launch Request and `(Host installation, Room)`.
3. When neither exists and the authenticated Fly envelope proves Genesis,
   insert one Run, promote every frozen participant and Spectator Membership
   into one Run Membership row, derive exhibition status from House
   Assignments, generate the public ID when required, release the
   `pre_genesis` reservation, attach the `active_run` reservation, append an
   applied receipt, and move the Launch Request to `run_created`.
4. When the existing identities and evidence digest are exact, return the
   original Run and append or return an idempotent duplicate disposition.
5. When any Room, operation, Genesis, Listing, roster, or evidence identity
   differs, append a conflict receipt and quarantine reconciliation. Never
   overwrite the mapping and never authorize a replacement Room.

The Host-mutation authorization transaction is the ordinary enforcement point
for account erasure. If authenticated Fly evidence nevertheless proves Genesis
after a violated or missing authorization boundary, `record_genesis_v1` still
inserts the one Run and exact Membership correspondence and then quarantines
the authorization conflict. It retains or creates an `active_run` reservation
using class `quarantined_recovery` when no authorized current row exists, even
if that temporarily exceeds the per-account or global gate. Gate checks count
both classes, so every new launch is blocked until the count is within the hard
limit. It never denies an existing authoritative Room or authorizes a
replacement.

A Launch Request may end without a Run only when the same transaction proves
that `host_mutation_started_at` is null, or authenticated Fly evidence proves
that the retained operation terminally failed before Genesis. Supabase
unavailability after Fly commits Genesis leaves a recoverable missing
correspondence; it does not authorize a new operation.

### Result reconciliation

Each hosted Run has a dedicated server-side result-indexer Spectator Membership
distinct from the optional Public Projection Relay. It has no participant
Action authority. Fly retains its credential; Supabase stores only the
Membership correspondence.

An authenticated Fly `ResultSourceEvidenceV1` response contains the exact Run
and Room correlation, Pack, result-indexer Membership and Spectator Access
Mode, latest observed Complete Head, Room-integrity status and generation,
Public Projection schema, canonical bytes, and `projection_hash`, plus an
optional Replay verifier revision, Replay Projection hash, and receipt through
that Head, and an envelope digest. It does not label the Head terminal and
contains no credential, private Projection, or Replay event bytes.

Vercel verifies the envelope against the immutable Run and Listing Revision,
loads the exact Result Projector Revision, and evaluates the authorized
Projection. Shared code does not infer Pack terminality:

1. Before terminal evidence exists, `not_terminal` leaves capacity and results
   unchanged. An older Head is stale. The same source or a valid strictly later
   Head after terminal evidence calls `record_terminal_conflict_v1`, suppresses
   any result, and does not reacquire capacity.
2. `terminal_without_outcome` calls idempotent `record_run_terminal_v1` to
   release `active_run` capacity but creates no result. If immutable terminal
   evidence already records `terminal_with_summary` at the same source or an
   ancestor Head, the locked RPC routes atomically to the terminal-conflict
   transition instead.
3. A schema-valid terminal summary calls the same terminal operation. When
   immutable terminal evidence already records `terminal_without_outcome` at
   the same source or an ancestor Head, the locked RPC routes to that conflict
   transition. Otherwise, when publication is disabled, Vercel discards the
   summary. When publication is enabled, healthy integrity and Replay
   verification through the same Head are mandatory. Under ADR 0025, the Host
   independently verifies the current and Replay hashes and their exact public
   content correspondence. Vercel hashes the verified historical public-view
   bytes supplied to the projector and requires the hosted evidence and Replay
   `projection_hash` to equal that hash before it calls `record_result_v1`.

`record_run_terminal_v1` retains only the projector identity, source Head and
evidence receipt needed to justify capacity release. It does not copy Activity
Phase or Outcome into the Activity Run.

For a publishable summary, `record_result_v1` behaves as follows:

1. No existing result and no conflict event plus exact valid evidence inserts
   evidence, payload, and an applied receipt atomically. Any terminal, result,
   integrity, or privacy conflict blocks insertion.
2. The same source evidence and summary digest returns the existing result.
3. A later Head producing the same summary adds a verification receipt but not
   another result.
4. The same source with a different summary, or a later projector-established
   terminal Head that changes the summary, atomically appends
   `result_conflict_quarantined` and its conflict receipt, suppresses any public
   result, and quarantines reconciliation. It never overwrites.
5. A pre-terminal `not_terminal`, missing Outcome, unhealthy integrity,
   unavailable or mismatched Replay, schema mismatch, digest mismatch, oversize
   output, or a suppressed, purged, or conflict-quarantined subject creates no
   public result.

Replay verification is required before the first publication. Healthy-at-
capture and Replay-verified are retained as separate evidence axes.

### Delivery and read repair

Fly may send Vercel an authenticated, best-effort opaque hint after Genesis,
Room progress that could change projector disposition, or a later integrity
change. A hint contains no Projection, Outcome, Membership credential, result,
or Supabase authority and is never accepted as evidence. Vercel always pulls
the fact from Fly.

The same idempotent reconciliation runs:

- after the ordinary launch or a result-source pull;
- when a creator reads Launch Request status;
- when an eligible Run page is read;
- after a Fly hint; and
- in one bounded once-daily Vercel Hobby sweep.

The daily sweep processes at most 100 candidates and always includes every Run
holding an unreleased `active_run` reservation, plus missing Genesis
correspondence, unpublished eligible results, and published results due for an
integrity recheck. Database
uniqueness is the correctness boundary, so duplicate or concurrent workers are
harmless. Lost, duplicated, delayed, or reordered hints do not change the
result.

Supabase unavailability blocks new platform mutations and delays Run/result
correspondence, but it cannot stop an admitted Room or direct Fly WebSocket.
Recovery resumes from the retained Launch Request and Host operation identity.

### Public result and attribution

The Listing Revision discloses its immutable publication policy before launch
or claim. `result_publication_policy` is the sole publication authority;
catalog visibility controls discovery only and cannot override it. A
participant joining `public_recent_results` accepts pseudonymous publication
under that reviewed policy; there is no post-Genesis per-Run opt-out. A
`disabled` policy creates no public result regardless of later catalog
discovery changes.

The public DTO contains only:

- public Run ID and safe Listing identity/copy;
- exact Listing Revision and Pack Revision display identities;
- Genesis and result times;
- evidence class and generic publication status;
- per-seat public label, Role, and participation type;
- optional current GitHub profile only when that account currently opts in;
- exact safe House Agent Revision, provider/model route, fixed allowance, and
  permanent `Exhibition -- platform-supplied agents` label; and
- the projector's bounded schema-valid public summary.

It never contains Room, setup-operation, Membership, Principal, Platform
Account, Supabase-row, invitation, token, credential, raw Projection, Replay,
prompt, or provider-response data.

External agents appear only as `External agent -- unverified`, with seat,
Role, controller pseudonym or opted-in current profile, and Pack-defined
result. The MVP ignores claimed model, provider, prompt, tool, skill, and agent
names. House Agents may disclose exact model information because the Platform
Operator controls their immutable assignment, but their Runs remain
exhibitions rather than benchmark evidence.

A later unhealthy or inconclusive integrity observation appends a suppression
event. Public reads then return only a generic unavailable state with no prior
summary or participant attribution. A strictly later healthy integrity
generation and matching verified Replay may append `result_reverified`; it
cannot override conflict, privacy, or purge events, and the immutable result
does not change.

`begin_account_erasure_v1` atomically tombstones the Platform Account and marks
its GitHub identity edge `erasure_requested_at`. In the same transaction it
locks the account's claims and owned Launch Requests. It releases every
unfrozen claim, cancels an owned unfrozen request, and marks any frozen request
whose first Fly mutation has not begun `failed_pre_genesis`; the applicable
capacity reservations are released. Once `host_mutation_started_at` exists,
erasure cannot rewrite the frozen roster or authorize a replacement Room. That
request continues exact reconciliation, but the erased account cannot enter;
if Genesis occurs, its correspondence remains pseudonymous and the normal
pre-start deadline can abandon an activity that cannot become ready.

`authorize_host_mutation_v1` locks every controlling account and rejects an
erasure before it atomically records the first Host boundary. An erasure after
that boundary cannot revoke an already-authorized operation's exact identities.
If Fly nevertheless proves Genesis after an earlier erasure or without the
boundary, `record_genesis_v1` records the one authoritative Run and quarantines
the authorization violation as specified above; it never discards the Room or
permits replacement. From the erasure commit onward every protected route
rejects the account mapping. The Auth Admin worker then hard-deletes the
Supabase Auth user; the Auth foreign key cascades the identity edge and Auth
removes its sessions and refresh tokens. The response clears the platform
cookie. If Auth deletion fails, the blocked pending edge remains available to
the bounded erasure reconciler for retry.

An already-issued access JWT can remain cryptographically valid until its
expiry, but it cannot reach the application data directly and the BFF can no
longer resolve it to an active Platform Account. Shared Runs and results remain
pseudonymized and linkable; the UI falls back to the reviewed seat label and
`Deleted participant`. Account deletion does not delete WorldStream history.
Exceptional legal or safety removal is an offline Platform Operator action
that suppresses before purging payload bytes and leaves a private digest
tombstone so reconciliation cannot resurrect them.

### Explicit MVP exclusions

This decision adds no Supabase Realtime, Edge Function, database webhook,
queue, materialized view, client-side Data API query, universal score,
leaderboard table, ranking endpoint, verified external-model claim, or
cross-Pack comparison. A future leaderboard is a separate projection over
eligible exact Listing Revisions and requires a separate decision.

## Verification

Implementation must prove all of the following:

1. `platform_store` is not exposed; `platform_api` is the only application
   Data API schema and contains only the enumerated functions.
2. `PUBLIC`, `anon`, and `authenticated` cannot read or mutate any base table
   or execute any application function. Inside `platform_api`, the deployed
   secret role can execute only the allowlist and cannot purge result payloads.
   Tests and operator docs also treat the secret as an elevated project master
   key, prove it never reaches browser or Fly, and cover rotation.
3. Every function is security-invoker, has an empty search path, uses fully
   qualified objects, and has explicit default and exact-signature grants.
4. Concurrent identical Launch Requests return one request; changed canonical
   input conflicts. Concurrent invitation claims have one winner and rotation
   invalidates the old digest atomically. Races admit one pending launch per
   account and exactly ten global Run reservations; acquisition, release, and
   ambiguous retries preserve both reservation lifetimes. House fill retains
   one claim window, candidate/exclusion set, draw, selection set, and exact
   Runner reservation attempt across every retry, and creates the immutable
   assignment set only after every retained reservation succeeds.
5. Crashes before the Fly call, after Fly Genesis, before Run insertion, and
   after insertion all converge to one Launch Request, one setup operation, one
   Room, and one Activity Run. An authorization-violating but Fly-proven
   Genesis is also recorded exactly once, quarantines, and blocks new launches
   if its retained capacity exceeds the gate. Inconsistent mappings quarantine.
6. Genesis creates exactly the frozen participant, creator-spectator,
   result-indexer, and optional public-relay Run Membership Correspondences.
   Re-entry resolves an authenticated account, Run, and stored opaque selector,
   never a Seat Claim or browser-supplied Principal/Membership ID; multiple
   seats controlled by one account resolve unambiguously. The same account
   receives distinct Principals in different Runs, while retries retain
   original IDs. Result indexers receive exactly attach, public-observation,
   and Replay scopes; public relays and creator spectators receive exactly
   attach and public-observation scopes.
7. The result registry has no Pack-name branch. Wrong Pack, Projection schema,
   projector digest, output schema, Head, integrity, or Replay evidence fails
   closed. Under ADR 0025, the original current and Replay hashes are verified
   independently, with exact same-Head content correspondence and only the
   prescribed viewer-class difference. The supplied projector bytes, hosted
   evidence `projection_hash`, and Replay `projection_hash` match exactly.
   Agent Heist and Negotiate use separate pinned projectors.
8. Result insertion, exact duplicate, later same-summary Head, and divergent
   summary are tested independently. A divergent valid summary atomically
   appends conflict quarantine and its receipt. A terminal disposition conflict
   or later nonterminal reversion does the same even before a result exists,
   permanently blocks publication, and never reacquires capacity. No normal
   application path updates or deletes immutable result evidence.
9. Public DTO tests prove the absence of every private identifier and prove
   pseudonym fallback after profile disable and account deletion.
10. House Runs always disclose exact revision and exhibition status; external
    agents never receive a verified model claim.
11. Dropped, duplicated, delayed, and reordered Fly hints converge through
    read repair and the daily sweep. Every unreleased active-Run reservation is
    swept, including publication-disabled and terminal-without-Outcome Runs. A
    result-only public ID cannot resolve on Fly's anonymous live endpoint.
12. Integrity-event permutations fold by greatest accepted generation rather
    than time: delayed old evidence cannot reverse new evidence, contradictory
    same-generation integrity status quarantines, a valid descendant Head at
    the same status and generation does not, and invalid evidence cannot
    suppress. Conflict, privacy, and purge remain unavailable after any later
    re-verification.
13. Every projector artifact and runtime referenced by a retained Run remains
    resolvable and executable after a newer release or catalog delisting.
14. One-use OAuth state, browser nonce, and PKCE verifier checks reject replay,
    expiry, missing-cookie, changed-return-target, and callback races. Session
    and OAuth cookies have the frozen attributes, rotate when required, clear
    with identical attributes, and never appear in cached responses.
15. Every listed lifecycle RPC has allow-and-deny tests. Erasure releases safe
    unfrozen claims and no-Host-mutation launches atomically, preserves exact
    reconciliation after the Host boundary, blocks all later entry, and
    retries Auth deletion without reviving the account. Pre-Host local failure
    uses locked platform evidence; every post-boundary failure uses matching
    authenticated Fly evidence.
16. Immutable catalog visibility changes discovery only. Result publication is
    determined solely by the accepted Listing Revision's publication policy.
17. Terminal disposition inserts one immutable terminal-evidence row and
    releases Run capacity atomically; exact retry, later confirming Head,
    conflicting disposition, and lost-hint daily recovery are tested.

Database migrations include their grants, default-privilege revocations, RLS,
constraints, indexes, and pgTAP allow-and-deny tests together. CI runs
`supabase test db`, `supabase db advisors`, schema-exposure checks, concurrency
tests, cross-system crash fixtures, and public-response privacy fixtures.

## Consequences

- The Hosted Activity Platform has one durable platform store instead of a
  second Fly-local coordination database.
- Supabase is authoritative for platform formation without becoming a second
  authority for Room activity.
- Vercel is trusted to verify the signed-in user, pull Host facts, run reviewed
  projectors, and write through a deliberately tiny function surface.
- Fly can continue running admitted Rooms while Supabase or Vercel is down.
- Result publication is delayed until verified Replay is available, favoring
  trustworthy evidence over immediate indexing.
- Result and attribution behavior works across Packs without adding a sixth
  Pack operation or a generic score model.
- Later community publishing, dynamic projector execution, leaderboards,
  verified external Agent Entries, and multi-installation operation require
  separate decisions.

This decision specializes ADRs 0019 through 0022. It does not change the
WorldStream Room Kernel, Activity Pack contract, or direct Fly WebSocket
architecture. Its single-project migration, credential, backup, and recovery
operation is frozen by
[ADR 0024](0024-operate-a-single-authority-hobby-preview.md).
